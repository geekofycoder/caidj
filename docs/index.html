Concurrency-Aware Indexing for Distributed Joins

The problem

A distributed join builds an index on the join key, then probes it. Classic algorithms assume the data holds still while that happens. In a live system it does not — writes keep arriving, and a lock on the index serialises them against every probe.

How each one works

All four implement the same BaseIndex interface, so the benchmark swaps them without touching the join executor.

NHJ — baseline

A standard distributed hash join behind one global reader-writer lock. Probes take the shared lock, writes take the exclusive one. This is the floor the others have to beat.

ECHI — epoch-based

Writes are batched into a delta buffer and applied all at once at an epoch boundary. Probes read a frozen snapshot and never take a lock at all. Fastest here at every level from 4 writers up, and the lightest on memory.

MPI-MVCC — versioned

Each key keeps a chain of committed versions, so a probe reads a consistent snapshot at its own timestamp without blocking. The read path is never blocked, but walking the version chain costs more than everything it saves in this workload.

BF-CSI — Bloom-filtered

A sharded Bloom filter sits in front of a concurrent skip-list and turns away keys that are definitely absent. Strong at low concurrency; skip-list write contention catches up with it as writers are added.

What to take from this

  • Concurrency-aware indexing is not an optimisation. The baseline blocks more than one probe in three at 16 writers. All three alternatives block none.
  • ECHI wins this workload. Lowest latency and highest throughput from 4 writers up, and it holds the least memory on average, because it keeps two hash maps during a transition rather than unbounded version history. The baseline is slightly lower at one writer, before contention inflates it.
  • MPI-MVCC is the honest negative result. Its read path is genuinely never blocked, but version-chain traversal over 50,000 tuples makes it the slowest protocol measured — worse than the baseline it was meant to beat. It would suit shorter version histories, not this one.
  • BF-CSI's Bloom filter barely fires here. About 7–8% of probes take the fast path. The index is built from R and probed with S's keys, both drawn from the same Zipfian distribution, so probes concentrate on exactly the keys R already holds — and the filter only fires on a definite absence. It is the second-fastest at one writer and falls behind as writers are added.

Limits

  • This is a simulator, not a cluster. Everything runs in one process on one machine. Network latency, node failure and partition rebalancing are not modelled. The numbers describe relative protocol behaviour, not absolute production performance.
  • These are recorded results, from the runs reported in the project. The page does not run the benchmark — build the simulator and run it yourself to reproduce them.
  • Memory is shown as absolute mean heap straight from the CSV. The report's Table 4.4 gives overhead relative to the baseline computed a different way; those two do not agree for ECHI and BF-CSI, so the raw figure is shown here.
  • Lock contention is a proxy. Cache-line invalidation and allocator pressure are not measured separately.
